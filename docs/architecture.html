claudekvm

An LLM-agent harness that operates a physical computer through a PiKVM — screen capture in, keyboard/mouse out — with dangerous-action guardrails. Exposed as a CLI and an MCP server.

1 · Overview

A PiKVM is an IP-KVM: it plugs into a target computer's HDMI and USB ports and exposes the screen as video and the keyboard/mouse as a USB HID gadget over a network API (kvmd). claudekvm wraps that API so an LLM agent can see the target (JPEG snapshots) and act on it (mouse/keyboard), with no software installed on the target. Because the agent reasons over pixels and emits USB input, the target OS is irrelevant — Windows, macOS and Linux are all driven the same way.

Two front-ends, one core. The CLI is for humans and shell-driven agents; the MCP server gives MCP-capable agents typed tools (with screenshots returned as inline images). Both call the same functions, so guardrails and behaviour are identical regardless of entry point.

The kvmd API surface the harness relies on (verified against kvmd 4.132 on a Pi Zero 2 W):

4 · Screen capture

kvmd suspends the streamer when no KVM client is attached, so a cold snapshot returns HTTP 503. The harness resolves this transparently: it briefly holds the /api/ws event socket open, which makes kvmd resume the streamer, then retries the snapshot. If snapshots remain unavailable it grabs a single frame from the MJPEG /stream.

sequenceDiagram
  participant A as Agent
  participant S as screen.capture()
  participant K as kvmd
  A->>S: capture()
  S->>K: GET /api/streamer/snapshot
  alt streamer active
    K-->>S: 200 image/jpeg
  else suspended (503)
    S->>K: open /api/ws  (wake streamer)
    loop up to 10× / 1s
      S->>K: GET /api/streamer/snapshot
      K-->>S: 200 image/jpeg
    end
  else still nothing
    S->>K: GET /stream  (one MJPEG frame)
    K-->>S: multipart frame
  end
  S-->>A: JPEG + (width, height) + source

Resolution is parsed from the JPEG with Pillow and cached, so subsequent mouse commands map pixels without re-capturing.

5 · HID input & coordinate mapping

Mouse events go over the kvmd WebSocket as absolute positions in a signed 16-bit range. Screen pixels are mapped with the same formula the PiKVM web UI uses:

kvm = int(pixel / size * 65535 - 32768)      # clamped to [-32768, 32767]
# (0,0)   → -32768   (top-left)
# center  → ~0
# (w,h)   → 32767    (bottom-right)

Keyboard input has two paths: bulk text uses the server-side /api/hid/print (layout-aware, fast); individual keys and combos use per-key WS key events with proper shift-wrapping and press-in-order / release-in-reverse for combos. A short flush delay before the socket closes ensures the final event is processed.

6 · Guardrails

Dangerous actions never execute silently. They are blocked with exit code 3 and a one-time token that a human must approve; the agent relays the token and waits.

What's gated

  • Typed destructive commands — shutdown, reboot, rm -rf, mkfs, dd if=, format, Stop-Computer, taskkill /f, … (cross-platform)
  • An Enter that would execute a dangerous command already typed (rolling keystroke buffer)
  • The Ctrl+Alt+Del power chord
  • Every ATX power action

How confirmation works

  • 6-hex one-time token, 10-minute expiry
  • Reused on repeat blocks so a valid token survives agent retries
  • Single-use: consumed on confirm
  • Every attempt (allowed / blocked / confirmed / executed) is appended to an audit log
stateDiagram-v2
  [*] --> Scan
  Scan --> Execute: benign
  Scan --> Blocked: dangerous, no token
  Blocked --> [*]: exit 3 + token (human must approve)
  Scan --> Verify: dangerous, token supplied
  Verify --> Execute: token valid & matches action
  Verify --> Blocked: wrong / expired token
  Execute --> [*]: audit "executed"
Boundary: the confirm-token prompt is the real safety boundary — keep a human in the loop for power actions. See §10 for the residual char-by-char evasion risk and its mitigation.

7 · The agent loop

The intended operating pattern, encoded in skills/pikvm-remote/SKILL.md: never fly blind — screenshot, decide one small action, act, then screenshot again to verify before the next step.

flowchart TB
  s["screenshot"] --> read["read image → identify OS / UI state"]
  read --> decide["decide ONE action"]
  decide --> act["move / click / type / key"]
  act --> verify["screenshot to verify"]
  verify -->|not done| decide
  verify -->|done| report["report to user"]
  act -.->|exit 3| block["surface token → human approves → confirm"]
  block --> verify

9 · Recommended models

Driving this harness well demands two capabilities working together: strong visual grounding (read a screenshot, locate a button, judge success) and reliable tool-use / function-calling (emit precise coordinates and command arguments, follow the screenshot→act→verify discipline). Long-context helps because each step carries prior screenshots. The table below reflects generally-available models as of mid-2026.

ModelFitWhy
Claude Fable 5 / Opus 4.8 AnthropicRecommendedTop-tier visual grounding and tool-use, native MCP support, strong at multi-step verify-as-you-go control. Best default for the MCP path.
Claude Sonnet 5 AnthropicRecommendedNearly the same computer-use quality at lower cost/latency — the pragmatic choice for high-volume or interactive sessions.
GPT-class vision + tools OpenAIWorkableSolid screenshot reasoning and function-calling; wire it to the CLI or via an MCP bridge. Coordinate precision varies by build.
Gemini 2.x Pro (vision) GoogleWorkableGood image understanding and long context; tool-calling reliability is the thing to validate for tight click targeting.
Hermes / open tool-use models localWorkableFine for the action side via the CLI; pair with a capable vision model for the see side, or use a vision-language checkpoint.
Text-only LLMs (no vision)Not suitableCan emit commands but can't read the screen — they'd act blind. Only workable if paired with screen_ocr for pure-text UIs, which is fragile.
Selection heuristic: prioritise (1) screenshot grounding accuracy, (2) coordinate/argument precision under tool-use, (3) instruction-following for the verify loop and guardrail protocol. A model that's brilliant at prose but loose with coordinates will misclick; a precise tool-caller that can't read the screen will act blind. You need both.

10 · Security & residual risk

  • Credentials live outside the repo — ~/.config/pikvm-agent/config.toml (chmod 600) or PIKVM_* env vars. .gitignore covers config, .env, state and audit files.
  • Audit trail: every input and power action is appended to ~/.local/state/pikvm-agent/audit.log.
  • TLS: verification is disabled for the device's self-signed cert. Trust is scoped to the LAN path to the PiKVM; this is not an internet-facing tool.
  • Residual evasion: an agent could type a dangerous command one character at a time via key events to dodge the text scanner. The Enter-evasion rolling buffer catches the common "type then Enter" case, and the audit log records everything — but treat the confirm-token gate as the real boundary and keep a human approving power actions.
